# 일상 운영과 권한 모델

## 역할별 운영 범위

SOAR는 운영 권한과 탐지 대상 권한을 분리합니다. 일반 사용자가 보안 운영 객체를 직접 조회하거나 정책을 바꾸지 않아도 백그라운드 탐지는 동작하도록 설계합니다.

| 기능 | 관리자 | 운영자 | Sites 게스트 | 일반 사용자 |
|---|:---:|:---:|:---:|:---:|
| 대시보드·감사 로그 조회 | 가능 | 가능 | 불가 | 불가 |
| 위협 시뮬레이터 | 가능 | 가능 | 불가 | 불가 |
| 정책·라우트 변경 | 가능 | 제한 | 불가 | 불가 |
| 스케줄 설정 | 가능 | 불가 | 불가 | 불가 |
| Drift 복구 | 가능 | 불가 | 불가 | 불가 |
| 인바운드 대응 수신 | 가능 | 가능 | 제한된 지점만 | 불가 |

## 운영 화면의 기본 흐름

### 대시보드

보안 점수, 최근 위협 타임라인, 채널별 요약, 심각도 필터, 감사 로그를 확인합니다. 로그 상세 화면에서는 탐지 정책, 유입 채널, 대상 리소스, 누적 횟수와 감사 추적 정보를 확인할 수 있습니다.

### 위협 시뮬레이터

실제 업무 데이터에 영향을 주지 않는 사전 정의 시나리오로 Platform, Data, Logic, Identity, External Signal 영역의 흐름을 점검합니다. 운영 전환 전에 이벤트 발행, 정책 매칭, 감사 기록과 알림 결과를 확인하는 용도로 사용합니다.

### 정책 매퍼

정책별 임계치와 대응 액션을 확인하고, 조직의 허용 범위에 맞게 조정합니다. 패키지 기본값과 런타임 설정이 달라지면 Drift 상태를 확인한 뒤 승인된 항목만 Reconcile합니다.

### 라우트 관리자

정책 코드, 심각도, 우선순위와 채널을 기준으로 알림 경로를 관리합니다. 동일 이벤트의 반복 알림은 중복 억제 창으로 제어하고, 일시적 전송 실패는 전달 원장과 제한된 재시도로 추적합니다.

### Teams 카드 버튼과 Site callback 주소

Teams 카드의 버튼은 두 종류의 목적지를 가질 수 있습니다.

- `사용자 상세 보기`: 로그인된 Salesforce 조직 화면으로 이동하는 조회 링크
- 보안 대응 버튼: Site 기본 주소 뒤에 `/services/apexrest/api/security/action`이 붙은 공개 REST callback

두 번째 링크가 Site 홈 화면이 아닌 REST 경로로 보이는 것은 정상입니다. 버튼 자체가 Site 페이지를 보여주기 위한 것이 아니라, 단기·단회 callback code와 승인 binding을 패키지 endpoint에 전달해 인바운드 요청을 처리하기 때문입니다. 브라우저의 GET 요청에는 HTML 결과 화면이 반환되고, 서버 간 호출에는 JSON 응답이 사용됩니다.

파괴적 액션은 독립 관리자 승인 전에는 카드에 실행 버튼이 나타나지 않습니다. 테스트와 운영 모두 요청자·대상·승인자를 구분하고, 관리자 계정을 테스트 대상에 직접 지정하지 않습니다. URL의 query 값은 재사용·공유하지 말고 새 카드로 다시 발송합니다.

### 스케줄 관리자

로그 보관, 정리, 감사 폴링과 실패 재전송 등 필요한 백그라운드 작업만 활성화합니다. 중복 등록 여부와 다음 실행 상태를 확인하고, 조직의 보존 정책에 맞춰 주기를 검토합니다.

### 모의 이벤트와 실제 전달의 구분

Threat Simulator, Trigger, Sec Facade, REST, LWC Event Bus의 UI 성공 메시지는 진입점·감사 기록·진단 기능을 확인하는 증적입니다. 실제 외부 전달을 검증하려면 다음 결과를 별도로 확인합니다.

1. 정책 이벤트가 생성됨
2. 정책 평가 결과가 `NOTIFY_TEAMS` 또는 조직이 선택한 액션으로 결정됨
3. `Delivery Ledger`에 Route와 Attempt가 생성됨
4. 최종 상태가 `DELIVERED`이고 외부 카드가 수신됨

승인 후 수동 액션 카드처럼 이 경로를 모두 통과한 경우에만 정책 기반 외부 전달이 완료된 것으로 판단합니다. 시뮬레이터의 성공 토스트만으로 Teams 전달 성공을 판정하지 않습니다.

### 결정자와 두 원장

정책에 걸린 대상 사용자와 실제 결정을 내리는 사람은 분리합니다. 카드의 Teams 수신자는 최종 결정자이며, 대상 사용자는 액션의 영향 대상입니다. 따라서 관리자 계정을 테스트 대상에 직접 지정하지 않고, 조직의 승인 책임자 또는 보안 운영 그룹을 결정자로 설정합니다.

- **Action Ledger**: 어떤 정책·액션을 실행할지, 누가 승인할지, 신원 확인이 필요한지와 같은 의사결정 상태를 기록합니다. 대표 상태는 `PENDING`, `APPROVED`, `REJECTED`, `EXECUTED`입니다.
- **Delivery Ledger**: 결정된 알림·액션을 Teams 같은 외부 채널로 전달한 결과를 기록합니다. 대표 상태는 `ACCEPTED`, `DELIVERED`, `FAILED`, `EXHAUSTED`이며 재시도와 Fallback 증적도 이 원장에서 확인합니다.

패키지에 포함된 Flow 템플릿은 이 두 원장을 관리하거나 최종 Teams 수신자를 결정하지 않습니다. Flow는 플랫폼 이벤트를 받아 Task를 만드는 선택형 보조 자동화이고, 정책 모드·결정자·Fallback·callback 실행 여부는 패키지 Apex와 원장 상태를 기준으로 확인합니다.

### Dashboard 승인과 Teams 결정의 관계

두 화면은 같은 일을 중복하는 것이 아니라 서로 다른 경계를 담당할 수 있습니다.

1. 정책 이벤트가 생성되면 패키지는 대상 사용자, 정책, 권장 액션과 결정 경로를 계산합니다.
2. 파괴적 액션은 Action Ledger에 `PENDING`으로 남고, 독립 승인자가 Dashboard 승인 대기열에서 실행 전제조건을 확인합니다.
3. Route가 `DASHBOARD`이면 Dashboard에서 최종 결정·실행 경로를 확인합니다.
4. Route가 `TEAMS`이면 승인 전제조건을 통과한 뒤 Teams 수신자가 카드에서 최종 승인·거절·실행을 결정합니다.
5. Route가 `BLOCK`이면 외부 카드나 실행 버튼을 열지 않고 차단 상태와 감사 기록을 남깁니다.

따라서 Dashboard에서 Teams 수신자를 정하는 것은 “관리자가 항상 액션을 대신 실행한다”는 뜻이 아닙니다. 정책과 심각도에 따라 최종 결정자 또는 보안 운영 그룹을 지정하는 설정 단계입니다. 카드 수신자는 실제로 판단할 사람이어야 하며, 액션 대상 사용자와 동일할 필요도, 시스템 관리자일 필요도 없습니다.

## 운영 원칙

- 파괴적 대응은 승인·권한·감사 원장을 함께 확인합니다.
- 외부 채널의 URL과 인증 값은 Salesforce Named Credential에서 관리합니다.
- 정책을 바꾼 뒤에는 시뮬레이터와 감사 로그로 의도한 결과를 확인합니다.
- 일반 사용자에게 운영 권한 집합을 광범위하게 할당하지 않습니다.
- 사용하지 않는 Zero-Login 지점과 스케줄은 비활성화합니다.
